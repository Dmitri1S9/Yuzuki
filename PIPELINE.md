## Этап 1. Каст

| Запрос | Проходов | Temp | Список на вход |
|---|---|---|---|
| `groups_medium` | 3 | 0.4 | нет |
| `groups_large` | 3 | 0.4 | нет |
| `groups_isolates` | 3 | 0.4 | нет |

Схемы раздельные: `GroupsOnlyResponse` для medium/large (без слота `isolates`), `IsolatesResponse` для изолятов. Общая схема протекает — модель кладёт в `isolates` всё, что не влезло.

### Канонизация имён — до всего остального

```
1. ō→o, ū→u, ou→o, uu→u, oo→o     всегда, хранить короткую форму
2. порядок снимается сравнением как множества токенов по пробелу, после п.1
   никаких списков фамилий не храним и известные фамилии не обрабатываем
3. множества пересеклись частично (один токен совпал, другой разошёлся)
   → ЛОГ, не сливать. Ручных шагов в пайплайне нет: обе записи остаются
   отдельными персонажами, дальше их судьбу решает порог ростера
```

Автоматическое голосование по частоте запрещено: на CotE большинство выбрало неверный вариант в двух случаях из четырёх (`Kyengo` вместо `Kyogo`, `Shin` вместо `Satsuki`).

### Сведение групп

```
medium    группа остаётся при 2/3; состав = union по выжившим проходам
large     2/3; состав = union по выжившим проходам
isolates  2/3
дедуп     medium ≥ 70% пересечения составов (Jaccard), large ≥ 50%
          large ниже: он делит весь каст на 1-2 масштабные фракции, и проходы
          дают одну и ту же фракцию разной полноты — на CotE состав короткого
          прохода оказался строгим подмножеством длинного (Jaccard 0.562,
          вложенность 1.000), при 90% такие не склеивались вообще
```

При коллизии типов приоритет `medium > large`.

### Ростер

```
keep = found_medium >= 2 or found_large >= 2 or found_isolate >= 2
```

Порог **внутри типа**, не сумма. Иначе он зависит от того, есть ли во вселенной large-группа.

Проверки в коде: `leader ∈ members` — дописать с логом; сверка medium↔large — кто прошёл порог в medium, но отсутствует в large, дописать.

Поля на персонажа: `group_count`, `mention_count`, `is_isolated` (из isolates-запроса, **не** из `group_count == 0`).

**Ростер замораживается.** Всё дальше — против него.

### Критерий членства в ростере (2026-09-08)

Точка (`time_period`) остаётся одиночной — список арок не вводим, слишком
много разночтений между вики по названиям. Меняется не точка, а то, кто
считается персонажем НА эту точку. В `system_prompt_groups.j2` (общий для
`medium`/`large`/`isolates`) добавлено:

```
List the characters relevant to {{ universe }} as of {{ time_period }}.
Include characters from the same storyline who are no longer present at this
point but whose actions led to it.
Do not include characters from unrelated storylines, or characters who first
appear after this point.
```

Три границы: своя сюжетная ветка (отсекает параллельные линии), «привели к
этой точке» (отсекает предысторию, которая к арке не ведёт), запрет на
будущее (утечка будущего отравляет предсказываемые связи — иначе персонаж
входит в ростер с чертами, которые модель на самом деле взяла из более
позднего канона). Выбывшие и погибшие в ростер попадают — именно они
проверяют первую границу.

Проверка на MHA Endeavor Agency Arc (единичный ручной прогон large×1 +
medium×1, без консолидации, без изолятов, без отношений — только чтобы
увидеть сырой прирост): 65 → 98 сырых имён. Часть — алиасы/варианты
транслитерации того, что уже было в ростере (`Enji Todoroki`↔`Endeavor`,
`Keigo Takami`↔`Hawks`, `Chiyo Shuzenji`↔`Chiyo Shuuzenji` — в реальном
пайплайне схлопнутся через LLM alias-resolution). За вычетом дублей — ~35
реально новых имён, и среди них два разных случая: (а) явно релевантные этой
арке герои/агентства/одноклассники, которых старый ростер просто не находил;
(б) вся фракция **Shie Hassaikai** (9 членов) — отдельная, разрешившаяся ДО
Endeavor Agency Arc сюжетная линия, вероятная утечка постороннего ("привели
к этой точке" читается моделью шире, чем причинно-следственная связь с самой
ареной). Решение по (б) — оставить формулировку как есть и смотреть на
результат полного прогона, не сузили заранее.

Полный прогон (3 прохода medium/large/isolates + алиасы): roster не
изменился (99, критерий членства — отдельный механизм от состава групп),
но `raw_clusters` вырос 139→152, `groups.medium` 5→9, `dropped_below_threshold`
16→30 — больше кандидатов всплывает, но лишнее (случайные упоминания,
не устоявшиеся структуры) корректно не проходит порог.

### medium — определение расширено на позиционные структуры (2026-09-08)

Первая версия правки добавляла только "family or dynasty" точечно в
Definition — по фидбеку пользователя это "гнуло" промпт в сторону одной
категории вместо общего принципа. Переписано на основе таксономии
структурных единиц:

```
Definition: a medium group is a stable structural position a character
holds — not something chosen by personal preference. Membership is defined
by role, rank, assignment, birth or place, not by who a character personally
likes.
```

Include расширен на 5 категорий вместо одной: (1) служебные/профессиональные
единицы — формулировка обобщена под "whatever term the universe itself uses"
(не всегда "agency"/"department" — в фэнтези орден, в космоопере экипаж);
(2) учебные когорты — без изменений по сути; (3) дом/фракция ВНУТРИ более
крупной организации (Hogwarts houses, Gotei 13) — отдельно от организации
целиком, конфликт между такими домами уходит в `group_relations`, не сюда;
(4) иерархия наставник→ученик, удерживается позицией, не выбором —
"Gran Torino→All Might→Deku" это цепочка, не компания равных; (5)
территориальная общность, где само место определяет связи; (6) семья/
династия — но только когда позиция в ней играет роль (наследник, глава
дома), не для каждого упомянутого родственника. Пункт про вид/происхождение
(квирклесс, маглорождённые) из таксономии сознательно не включён — по
природе это чаще признак масштаба всего общества, то есть `large`, не
`medium`; если понадобится — отдельная правка `large`, не эта.

Тест на MHA Endeavor Agency Arc, один прогон medium: вышли "Todoroki Family"
(семья), "One For All Successors" (наставническая цепочка Yoichi Shigaraki→
...→Nana Shimura→All Might→Deku), "The Big 3" (дом внутри школы),
"Paranormal Liberation Front Leadership" (фракция внутри большой группы) —
все новые категории сработали, не только семья. Явного мусора не замечено.

Старая версия промпта сохранена рядом:
`user_prompt_groups_medium_v1_backup.j2` (не используется кодом, только для
сравнения/отката).

### Побочные находки при полном прогоне с новым промптом

**Алиас-подтверждение переработано** (`stage1_cast.py`, `build_alias_pairs`).
Первая версия правки просто снизила `ALIAS_MIN_HITS` 2→1 — по итогу признано
шумом (один непарный hit из одного прохода ничего не гарантирует). Настоящая
идея: полный ростер имён и так подаётся кандидатами в КАЖДЫЙ из 3 alias-
проходов (без фильтра по частоте встречаемости — это не менялось и не было
узким местом), значит у пары есть шанс на **взаимное** согласие внутри ОДНОГО
прохода — модель независимо говорит и "A, другое имя — Б", и "Б, другое имя —
A" в одном и том же вызове. Это сильнее одного направления из одного прохода
и не требует второго независимого подтверждения. `ALIAS_MIN_HITS` вернули на
2, но пара теперь проходит **либо** при 2 отдельных проходах (как раньше),
**либо** при взаимном согласии в одном проходе. `Dabi ↔ Toya Todoroki`
ловится этим механизмом — 21 алиас всего, ровно как и при временном
снижении порога, но без ослабления защиты от случайных совпадений.

**`max_output_tokens` 32768→65536** (`clientGemini.py`, все типы запросов —
общий метод) — при выросшем от нового medium-промпта списке кандидатов (152
сырых кластера) `alias_names()` стабильно (дважды подряд, не транзиентно)
обрывался на JSON примерно в одном и том же месте — thinking level "medium"
+ вывод по одной записи на каждое имя вместе упирались в старый лимит.
65536 — потолок модели (`gemini-3.8-flash`), проверено через API
(`client.models.get(...).output_token_limit`).

**Даби (Dabi/Toya Todoroki) после обеих правок**: 1 связь → 3 (`against`
Enji Todoroki — нашлась именно через medium-scoped запрос по "Todoroki
Family", и отдельно через general_pool; `against` Hawks). Связь Dabi↔Shoto
Todoroki по-прежнему не нашлась ни разу — открыто, не решено: либо
оставшийся пробел сборки, либо канонически корректное отсутствие (по
сюжету на этой конкретной точке Шото ещё может не знать/не осознавать
личность Дабi — раскрытие происходит позже). Не разбирались, что из двух.

## Этап 2. Признаки

**(2026-09-08) Порядок в пайплайне сменился: теперь Этап 3 (отношения) идёт
ДО Этапа 2 (признаки)**, см. `run_pipeline.sh`. Причина — `low_info`-фильтр
ниже: чтобы не тратить API на персонажей с 0 связей, нужно сначала узнать, у
кого 0 связей, а это знает только Этап 3. Раньше порядок был 2→3, но
технической зависимости между ними не было (оба независимо читают только
ростер Этапа 1) — реордер ничего не ломает.

**Оценка на момент выбытия.** С тех пор как выбывшие/погибшие попадают в
ростер (см. Этап 1 → Критерий членства), признаки для них нужно снимать не
на саму точку `time_period` (там их уже физически нет), а на момент их ухода
из истории. Правило `system_prompt_ranker.j2`/`system_prompt_flagger.j2`
(заменило старое "judge strictly within the time period", которое не
покрывало этот случай):
```
Evaluate characters by their state at {{ time_period }}, or at the point they
left the story if that came earlier.
```
Без этой оговорки модель тянет позднюю версию персонажа из общего знания
канона — а не то состояние, которое реально соответствует их последнему
появлению в этой сюжетной ветке.

|---|---|---|---|---|
| Ординалы (6) | 6 | 3 | 0.1 | 2048 |
| Флаги (51) | ~14 | 3 | 0.1 | 1024 |
| Категориальные + абсолютные | ~2 | 3 | 0.1 | 1024 |

Ростер подставляется в промпт. Калибровка тиров — абстрактные архетипы без имён реальных персонажей, как сейчас.

### low_info — персонажи без сигнала пропускаются

`stage3_relations.py` считает `low_info_characters`: персонаж с **менее 2**
различных связей (`LOW_INFO_MIN_DEGREE = 2`) И не подтверждённый как изолят
отдельным промптом — это не то же самое, что изолят (изолят — позитивно
определён как "одиночка по сюжету"; low_info — модель просто мало что про
него сказала). Список пишется в `relations_merged_{slug}.json`.

**(2026-09-11) Порог поднят с "0 связей" на "<2 связей".** Одной, тем более
однонаправленной связи недостаточно, чтобы считать персонажа осмысленно
описанным — конкретный случай: `Kinoko Komori` формально имела 2 сырые
записи, но это была ОДНА и та же связь (`Shihai Kuroiro → Kinoko Komori,
want`), просто найденная независимо на двух уровнях (medium И general_pool).
Наивный подсчёт сырых записей посчитал бы это за 2 и пропустил бы её мимо
порога. Правильно: дедуп по `(пара, тип)` — та же связь с разных уровней
схлопывается в одну ДО подсчёта степени, только после этого сравниваем с
порогом. Изоляты по-прежнему исключены из правила — 0 или 1 связь у изолята
это позитивный сигнал ("одиночка"), а не недостаток информации.

`stage2_features.py` читает этот список (если файла нет — предупреждение и
работа по всему ростеру, без падения) и **не запрашивает** ранги/флаги для
low_info-персонажей — реальная экономия API, не постфильтр. Они остаются в
выводе: `roster` теперь список объектов `{"name", "low_info"}` (было — плоский
список строк), `features[name]` для low_info-персонажа — `null` целиком (не
по параметру). `null_share_per_param`/`quality.consensus` считаются только по
реально опрошенным (`collect_roster`), low_info не в знаменателе.

Замер (порог "≥2 связи"): MHA Endeavor Agency Arc, ростер 106 — 48 low_info
(45%). Числа CoTE (5/41) и более ранние MHA-замеры выше по тексту сессии
считались ещё по старому порогу "0 связей" — не сопоставимы напрямую,
пересчёт по новому порогу на CoTE не делался.

На графе (`stage4_graph.py`) low_info помечены отдельно от изолятов (светлая
заливка, точечная рамка, не путать с серой заливкой изолята) — тот же список
`low_info_characters`, не пересчитывается заново, чтобы маркер на графе и
исключение при сборе признаков никогда не расходились.

**Следствие для валидации, знать заранее.** `low_info` определён через
отношения (Этап 3), значит в датасете структурно не может быть примера
«полный профиль признаков, ноль связей» — такой персонаж по построению
получает `features: null`, а не полный профиль. Отрицательные примеры (для
любой будущей модели, предсказывающей связи по признакам) остаются только
среди персонажей, у которых есть хотя бы одна связь. Выборка сужена в
предсказуемую сторону — это нужно знать ДО этапа валидации/моделирования, а
не обнаружить на нём в виде необъяснимого перекоса.

### Сведение

**Ординалы: консенсус-ранжировщик (2026-09-08), `ordinal_consensus.py`**

Решает оба открытых пункта, которые раньше стояли здесь (тай-брейки внутри
тира ломали order Kappa на боевых арках; было неясно, усреднять ли
`within_normal` или хранить только тир). Вместо голосования по номеру тира
и правила "размах ≥2 тира → null" — консенсусный слабый порядок (weak order):
персонажи группируются в упорядоченные блоки, внутри блока — равны.

Метрика: каждый из 3 проходов сводится к попарным меткам `L_i(a,b) ∈ {>,<,=}`,
`=` — когда a и b в одном тире ЭТОГО прохода (метка берётся с уровня тира, не
позиции). Кандидат-порядок сводится к тем же меткам по номеру блока.
`kappa_i` = Cohen's kappa на этих метках. Цель — максимизировать
`(kappa_1, kappa_2, kappa_3)` отсортированный по возрастанию, лексикографически
(maximin: сначала тянем вверх худшую каппу). Пары, где у прохода нет данных
хотя бы по одной стороне, из kappa_i этого прохода исключаются (маска), как и
раньше делал R для NaN-скоров.

Алгоритм: Borda-инициализация (средний скор по проходам) → соседи склеиваются
в блок, если нет большинства 2/3 за строгое разделение по тиру → hill climbing
(merge/split/перенос элемента в соседний блок или в любой блок в окне ±5
позиций/swap соседних блоков), первое улучшение маximin-вектора принимается,
сходимость — полный проход без единого принятого хода → 5 рестартов со
случайным возмущением инициализации, берётся лучший по тому же maximin-ключу.

**Жёсткий пол — majority tier.** Без ограничений kappa-оптимизация готова
слить в один блок персонажей с РАЗНЫМИ исходными тирами, если так согласие
выше — поймано вживую на `authority_scope`: блок из 27 человек включал тиры
0, 1 и 2 одновременно. Фикс: у каждого персонажа считается majority tier
(тир с ≥2 голосов из 3 проходов, та же логика что в `merge_cell`; при 1/1/1
или <2 проходах — не определён, такой персонаж ничего не ограничивает).
Merge и перенос элемента в другой блок запрещены, если у обоих (блока и
элемента) majority tier определён и различается. Split ничем не ограничен —
дробить тир на более мелкие блоки можно всегда, объединять разные тиры
нельзя никогда. Проверено на реальных данных: 0 нарушений на всех 57
параметрах (6 ординалов + 51 флаг) прогона CoTE.

Корректность метрики и ограничения проверена 4 свойствами (unit-тест в
`ordinal_consensus.py`, `python ordinal_consensus.py`): кандидат "всё в одном
блоке" даёт kappa=0 на всех трёх проходах; кандидат "строгий порядок без единой
связи" проигрывает консенсусу на данных с реальными тир-равенствами; истинная
блочная структура достигается или превосходится оптимизатором; ни один блок
не смешивает два разных majority tier.

Правило "размах ≥2 тира → null" снесено вместе с внедрением — неопределённость
теперь в размере блока и в `pass_range` (последний хранится всегда, не только
когда <2). Старое поведение можно посчитать рядом для сравнения одним прогоном:
`python stage2_features.py ... --legacy-null` — временный флаг, только для
сверки, будет удалён.

Выход на персонажа (вместо `value/confidence/mean_within`):
```
block_index   int, 0 = верх
block_size    int
consensus_z   float, z-score по midrank блока среди всех размещённых
pass_range    int, max−min тира по доступным проходам, всегда
```
Персонаж, у которого <2 проходов дали тир — не размещается, `null` (та же
логика "недостаточно данных", что была раньше, не путать со снесённым
правилом про разногласие).

**Три разных reliability-метрики, ни одна не заменяет другую — все хранятся,
и все три считают согласие по-разному, не только по разным категориям.**

- `min_kappa` (Python, `ordinal_consensus.py`) — реальные проходы против
  СГЕНЕРИРОВАННОГО 4-го прохода (сначала ранги фиксируются правилом majority
  tier, потом в их рамках строится blocks-порядок, максимизирующий kappa со
  всеми тремя реальными проходами разом — это и есть "4-й проход"). Сэмпл —
  ПАРА персонажей, категория — их взаимное отношение (`>`/`<`/`=`). По сути
  goodness-of-fit подогнанной модели, не inter-rater reliability.
- `kappa_raw_12/13/23` / `kappa_raw_min` (Python, та же попарная выборка, тир
  модели как категория) — реальные проходы ДРУГ С ДРУГОМ, без генерации.
- `tier_min` / `tier_12` (R, `kappa_analysis.R`) — тоже реальные проходы друг
  с другом, тир модели как категория, но сэмпл — ОДИН ПЕРСОНАЖ (классический
  Cohen's kappa: совпал ли у двух проходов абсолютный тир этого персонажа),
  не пара. Из-за этого `tier_min` и `kappa_raw_min` — РАЗНЫЕ числа, даже
  считая по одному и тому же тиру одних и тех же проходов (см. таблицы:
  расхождение до 0.15, не округление). `order`/`order_min` (квартиль позиции
  в ростере, не тир модели) из R убран целиком (2026-09-08, по прямому
  запросу) — не давал ничего сверх `tier_min`, только путал спор о позиции
  внутри тира с реальным разногласием. Фильтр `verdict()` в R теперь гейтится
  на `tier_min` вместо `order_min`, `bucket_min` — вторичный (был только
  информационным).

Выход на параметр (`quality.consensus.<param>`, применяется и к ординалам, и
к флагам — см. ниже):
`kappa_vs_pass1/2/3`, `min_kappa` (против сгенерированного, попарная выборка) —
`kappa_raw_12/13/23`, `kappa_raw_min` (реальный против реального, попарная

### Валидация

`kappa_analysis.R`, per-персонаж Cohen's kappa (не попарная по парам
персонажей — см. отличие от `kappa_raw_min` ниже), считается по-прежнему на
обоих: 6 ординалах и 51 флаге.

```
kappa_12   попарно 1×2
kappa_min  минимум из 1×2, 1×3, 2×3 — рабочая метрика (не медиана)
```

`kappa_min` — худшая из трёх пар проходов, не медиана. Параметр обязан быть согласован
на **каждой** паре независимых проходов, а не на большинстве — это жёстче стартовая
планка, специально принята как более консервативная.

**(2026-09-08) `order` (квартиль позиции в ростере, `cat_order` — ранжирование
всех персонажей прохода и деление на 4 равные группы) удалён из
`kappa_analysis.R` целиком.** Не давал ничего полезного сверх `tier`: квартиль
не привязан к тирам самой модели, поэтому спор о позиции ВНУТРИ тира (который
`ordinal_consensus.py` теперь решает блоками, см. выше) ошибочно читался как
разногласие по order, хотя по тирам прохода реально совпадали. Фильтр
переехал на `tier` как основной гейт:
- tier < 0.5, либо не вычисляется (NA) → параметр отбросить
- tier ≥ 0.5, bucket ≥ 0.5 → continuous-valid, z-score
- tier ≥ 0.5, bucket < 0.5 (в т.ч. NA) → categorical-valid, только тир

Bucket теперь участвует в фильтре (раньше — только информационно).

**Порога `>40% null` по параметру нет.** Отбрасывался целиком по вселенной — это
убивало редкие, но настоящие черты: 2-3 персонажа во вселенной с флагом, который
у всех остальных не проявляется, стирались вместе с шумом. Null остаётся только
**поячеечно** (см. Этап 2 → Сведение → Флаги/Ординалы): для конкретного персонажа,
если модель не набрала кворум 2 из 3 проходов. Для остальных персонажей значение
параметра сохраняется, даже если он null почти у всех.

## Этап 3. Отношения

**(2026-09-08) Переработано — 3 независимых контекста сбора вместо одного
общего пула, `stage3_relations.py`.**

| Контекст | Вход | Что | Реализация |
|---|---|---|---|
| medium-группы | только члены ОДНОЙ medium-группы | отдельный запрос на каждую группу, все 4 оси | готово |
| общий пул | весь каст, с редукцией звёзд между раундами | 3 раунда, все 4 оси в каждом | готово |
| между группами | имена групп (large + medium вместе) | пары союзников / пары соперников | готово |

`for`/`against`/`want`/`with` — всегда 4 отдельных запроса, никогда не
объединяются в один вызов модели, ни при каком размере списка.

**Семантика намеренно отличается от Этапа 2 (2026-09-08).** Признаки —
СРЕЗ на `time_period` (или на момент выбытия, см. Этап 2). Отношения —
НАКОПЛЕННЫЕ до этой точки, включая связи с персонажами, которых на
`time_period` уже физически нет в истории (они всё ещё в ростере — см. Этап
1 → Критерий членства). Это не расхождение, которое нужно унифицировать —
у среза и накопления разный смысл по построению, и путать их нельзя: если
где-то в будущем отношения тоже урежут до среза, это надо делать осознанно,
не молча.

### Правило по длине списка (`collection_plan`)

Применяется к списку, который реально уходит в запрос (члены medium-группы,
или текущий сокращённый общий пул) — не к имени уровня:

| Длина списка | Проходов | Temp |
|---|---|---|
| ≤ 15 | 1 | 0 |
| 16–35 | 2 | 0.4 |
| > 35 | 3 | 0.4 |

temp=0 только когда проход один (максимум правдоподобия, разнообразие не
нужно); 0.4 как только проходов больше одного.

### Star reduction — только на общем пуле

3 раунда фиксированно (не до сходимости). Раунд 1 — весь ростер. После
раунда, если он не последний: считается суммарная степень персонажа по всем
4 осям СРАЗУ за этот раунд (один общий цикл, не 4 отдельных — участие в
нескольких типах отношений усиливает "звёздность", не считается отдельно по
типу), берётся максимум M, из списка убираются все со степенью в `[M-2, M]`,
но только если под условие попадает ≥3 человек — иначе редукция в этот раунд
не применяется, список остаётся как есть, раунд всё равно засчитывается.
Раунд 2 и 3 идут по (возможно) сокращённому списку.

Убранные персонажи не пропадают из данных — их рёбра из более ранних раундов
остаются в объединении, они просто не могут быть названы моделью в
последующих (более сфокусированных) раундах.

На CoTE (41 чел.) реальная редукция ни разу не сработала за все 3 раунда —
степень распределена достаточно ровно, не нашлось ≥3 персонажей в верхней
полосе `[M-2,M]`. Не баг: правило консервативное по конструкции (адаптивный
порог был выбран специально, чтобы не резать зря на разреженных вселенных).

### Сведение — union, порога нет, pass_count не суммируется между уровнями

```
пара/клика попадает в граф, если её назвал хоть один запрос любого уровня
pass_count — счётчик ВНУТРИ уровня (medium — все раунды одной группы вместе;
            general_pool — все 3 раунда вместе, это ещё один уровень, не 3)
source_level пишется на каждом ребре (medium:<Class 1-D> / general_pool)
```

Если одна и та же пара всплыла и в medium, и в general_pool — это ДВЕ
отдельные записи с разным `source_level`, не одна объединённая (разная
уверенность у "нашли 1 раз из 1 в группе" и "нашли 1 раз из 3 в общем пуле",
схлопывать их в общий счётчик значило бы уравнять то, что не равно).

Симметричные отношения (`with`/`against`) хранят клику как есть (2 = пара,
3+ = группа) — не разбиваются на пары. Разбиение на пары применяется только
внутри подсчёта степени для star reduction, не в итоговом выводе (был баг:
первая версия мёржа случайно использовала ту же разбивку и для вывода —
клики схлопывались в пары, `has_small_group` уходил в 0; исправлено).

Постфильтр: имя не из списка, который реально ушёл в запрос (члены группы
для medium, текущий пул для general_pool) → отбросить, залогировать.

**Найдено вживую на CoTE:** medium-группа "Class 1-D" в `stage1_cast` содержит
2 персонажей ("Satsuki Shinohara", "Keisei Yukimura"), которых нет в
основном ростере — тот самый ранее отложенный вопрос "жив в группе / не жив
в ростере" (см. историю сессии), раньше он был незаметен, потому что старый
Этап 3 брал только ростер целиком, а не списки членов групп. Не решая
вопрос по существу, `merge_medium` теперь пересекает список членов группы с
ростером перед постфильтром — персонаж, отсутствующий в ростере, никогда не
попадёт в сохранённые отношения, даже если он есть в списке группы, которую
реально спросили.

`has_small_group` = участие в клике `with` от трёх человек.

`system_prompt_group_relations.j2` / `user_prompt_group_relations.j2` +

искусственно занижен — весь смысл сравнения (модель S vs модель P на 63
признаках личности vs полная) в том, чтобы у S был честный шанс.

Ключ = `sha256(system_prompt + user_prompt + pass_number)`. Хэш от семантических аргументов недостаточен — правка текста промпта тихо вернёт старый ответ.

## Логи качества, на вселенную

```
доля имён без матча с ростером
разброс числа пар между проходами
доля рёбер с pass_count = 1
число групп по типам
доля null по параметрам
```

Это критерий готовности при переходе на новые вселенные: резкий скачок означает, что промпт не держит жанр.

---

## Что не входит в пайплайн

Проекция групп в рёбра, блокмодель, веса рёбер, шипы, обучение. Всё после того, как данные по трём-четырём вселенным лежат и просмотрены.

## Сознательные отклонения кода от спеки (на текущий момент)

Решено оставить как есть, до отдельного захода:

- **Схема групп.** `GroupsOnlyResponse` не заводится: medium/large продолжают использовать общий `GroupsResponse` со слотом `isolates`. Протечка, описанная выше, остаётся возможной.
- **Флаги не батчатся.** 51 флаг = 51 запрос, а не ~14.
- **Thinking budgets** прежние: ординалы 1024 (не 2048), флаги 0, категориальные 0.
- **`location`** присутствует в сигнатурах и шаблонах, но никогда не заполняется — всегда пустой. Ключ вселенной в БД пока `(name, arc)`, без `location`.
- **Хранение отношений.** Таблица `edges` не заводится. Остаётся `relations`: строка на *(тип, проход)*, симметричные клики целиком в JSONB-поле `members`, без разложения на пары. Формат читаемый и экономнее по памяти; агрегация до вида «ребро + `pass_count`» делается на лету в `merge_relations.py` → `relations_merged.json`.

### ОТКРЫТО, вернуться позже: Batch API

Не сделано в этот заход — не замена одного параметра, а смена модели
выполнения. Batch API — это submit-job-and-poll, а не синхронный
call-and-get-result, на котором построен весь текущий пайплайн (`client.rank()`
и т.п. вызываются по одному в цикле, каждый сразу отдаёт результат). Нужно:
собрать все ожидающие запросы вперёд одним списком вместо цикла,
отправить одной batch-джобой, дождаться (может занять часы, не секунды),
сопоставить результаты обратно с (тип задачи, параметр, номер прохода),
развести с Redis-кешем (сначала исключить уже закешированное, в batch
уйдёт только новое). 50% скидка на вход и выход — весомая, но это отдельная
архитектурная задача, не быстрая правка.
